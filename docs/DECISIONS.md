# Architecture Decision Records

ADR-001 to ADR-012 record the first build of this platform. Where the Landing Zone integration changes one, the status line says so. ADR-013 onward are new.

One entry per decision the project plan does not spell out: what, why, what was rejected.

## ADR-001 - EKS 1.35 for the baseline cluster

- **What:** The baseline cluster runs Kubernetes 1.35 on EKS, with the AL2023 managed node AMI. The original workload was built on 1.30.
- **Why:** EKS no longer offers 1.30 in us-east-1 (`aws eks describe-cluster-versions`, checked 2026-10-16: oldest available is 1.31, in extended support). The workload installs Istio with istioctl 1.30.2, and Istio 1.30 supports Kubernetes 1.32 to 1.36 (istio.io supported releases page). The versions in EKS standard support are 1.34, 1.35, 1.36 and 1.37, so 1.34, 1.35 and 1.36 satisfy both. 1.35 stays in standard support until 2027-03-27, so it never bills the extended-support rate during the build, and it sits inside Istio's range rather than at its edge. Amazon Linux 2 node AMIs are not published for 1.33 and later, so the node group moves to AL2023.
- **Rejected:** 1.34 (standard support ends 2026-12-02, too close); 1.36 (the newest version Istio 1.30 supports, with no margin); 1.37 (outside Istio 1.30 support); upgrading Istio at the same time (two changes to the baseline instead of one).

## ADR-002 - Partial backend configuration kept out of git

- **Status:** Superseded by ADR-013 (state lives in the Landing Zone state bucket; no bootstrap stack).

- **What:** The stacks declare `backend "s3" {}` and load the bucket name from `infra/backend.hcl`, generated by the bootstrap stack and git-ignored. The bucket name uses a random suffix instead of the account ID. Locking uses S3 native lock files (`use_lockfile`), with no DynamoDB table.
- **Why:** The repository is public from day one, and backend blocks cannot use variables, so a literal bucket name would publish an account-linked identifier.
- **Rejected:** A bucket name built from the account ID (leaks the ID). A DynamoDB lock table (an extra resource, no longer needed since Terraform 1.10).

## ADR-003 - Bootstrap stack state stays local

- **Status:** Superseded by ADR-013 (the bootstrap stack was removed).

- **What:** `infra/backend` keeps its own state on the build machine (git-ignored). It holds only the state bucket and the budget.
- **Why:** The stack creates the bucket the others store state in. Migrating its state into its own bucket adds a circular dependency for two resources that are destroyed last.
- **Rejected:** Migrating the bootstrap state into the bucket after creation.

## ADR-004 - Changes made to the original workload when copying it

- **Status:** Amended: the baseline no longer creates a VPC, NAT or ECR repositories (ADR-014, ADR-015).

- **What:** The baseline is the original platform with only these changes: Kubernetes 1.35 and AL2023 nodes (ADR-001); a partial S3 backend (ADR-002); provider default tags `Project=zero-trust`, with the original `Project` tag renamed `Workload` so it does not override it, and `Project` repeated on the EKS module tags so node instances carry it; a tag annotation on the Istio ingress gateway service so its load balancer is tagged; account-specific Helm values (ECR URLs, IRSA role ARNs, queue URLs) removed from the values files and injected at deploy time from Terraform outputs; the simulator reads its target from `API_BASE_URL` instead of a hardcoded load balancer hostname; comments, descriptions and log messages translated to English, emojis removed. Network layout, security groups, public ingress, NAT and IAM policies are unchanged.
- **Why:** The "before" measurement must describe the original exposure, so nothing that affects reachability is touched. The other changes are required to deploy in a new account, to tag every resource for cleanup verification, and to publish the code without account identifiers.
- **Rejected:** Redeploying the Prometheus, Grafana and Kiali sample addons: they are ClusterIP services that do not change the exposure being measured, and on two t3.medium nodes (the account allows 5 vCPU) their memory is better left to the workload and the security tooling added later.

## ADR-005 - One firewall endpoint and single-AZ interface endpoints

- **Status:** Retained. Production changes to one endpoint per zone (`endpoint_az_count = 2`; firewall endpoints per zone is on the roadmap).

- **What:** The Network Firewall has one endpoint, in the first availability zone, and both public subnets route through it. The interface VPC endpoints are also placed in that one zone. The workload itself still spans two zones.
- **Why:** The whole project has a hard cost cap of 10 USD. A firewall endpoint costs 0.395 USD per hour and each interface endpoint 0.01 USD per hour per zone (AWS Pricing API, us-east-1). One firewall endpoint instead of two saves 0.395 USD per hour, more than the rest of the retrofit combined. Cross-zone traffic through one endpoint is functionally correct.
- **Rejected:** One firewall endpoint per zone (the production pattern: a zone failure would not take inspection down with it, and no cross-zone traffic charges). Recorded as the change to make for production.

## ADR-006 - Retrofit changes to baseline-owned resources go through baseline variables

- **What:** Making the EKS API private changes an attribute of the cluster, which the baseline stack owns. The baseline stack exposes `zero_trust_private_api` (default `false`, the original value); the retrofit applies the baseline again with it set to `true`. Every other control lives in `infra/zerotrust` and only adds resources. Once the API is private, kubectl reaches it through a Session Manager port-forwarding session to a node (`scripts/kube_tunnel.sh`).
- **Why:** One owner per resource avoids two stacks fighting over the same attribute, and the default still reproduces the original platform exactly. Restricting the public endpoint to one IP address instead would leave a reachable API from the machine that runs the external scan, so the scan could not show it closed.
- **Rejected:** Editing the cluster from the zerotrust stack (drift and conflicting state); keeping the public endpoint with an IP allowlist (still an internet-facing API).

## ADR-007 - Two /1 routes instead of replacing the public default route

- **Status:** Amended: the /1 routes and the IGW edge route table now touch Landing Zone-owned route tables, so they are gated by `inspect_public_subnets` (ADR-016).

- **What:** The public route table keeps the baseline `0.0.0.0/0 -> internet gateway` route, and the zerotrust stack adds `0.0.0.0/1` and `128.0.0.0/1` pointing to the firewall endpoint. Longest-prefix match sends all internet-bound traffic from the public subnets (load balancer replies, NAT egress) through the firewall.
- **Why:** The default route belongs to the baseline VPC module. Two more specific routes achieve the same path without editing or importing a resource another stack owns. The internet gateway edge route table sends inbound traffic for the public subnets to the same endpoint, so both directions of every flow go through it (stateful inspection needs symmetric routing).
- **Rejected:** Re-associating the public subnets to a new route table (the baseline already owns the associations); importing the module's route into this stack.

## ADR-008 - VPC endpoints chosen from what the workload calls, NAT kept behind the firewall

- **Status:** Amended: the Landing Zone VPC has no NAT, so the NAT-behind-firewall design is replaced by ECR mirroring (ADR-015). Endpoints are created only when the Landing Zone does not provide them.

- **What:** Gateway endpoints for DynamoDB and S3. Interface endpoints for ECR (api, dkr), EC2 (VPC CNI), STS (IRSA), EventBridge, SQS, DynamoDB Streams, and SSM, SSM Messages, EC2 Messages (Session Manager). No Secrets Manager endpoint. The NAT gateway stays, but every packet it sends to the internet goes through the firewall, which only passes TLS to Docker Hub domains.
- **Why:** The list comes from the code: the five services call DynamoDB, DynamoDB Streams, EventBridge and SQS, pods get credentials from STS, nodes need ECR and EC2. None of the services reads a secret, so a Secrets Manager endpoint would be a resource with nothing behind it. The NAT gateway cannot go: Istio's proxy image is pulled from Docker Hub each time a pod starts, and removing NAT would break the next pod restart. Keeping it behind a deny-by-default allowlist leaves no open egress path, and the egress drop rule gives a second blocked-path demonstration.
- **Rejected:** Removing NAT and mirroring the Istio images into ECR (more moving parts in the baseline workload than the project is about); a Secrets Manager endpoint with no caller.

## ADR-009 - Network Firewall alerts reach Security Hub through a custom Lambda

- **What:** A CloudWatch Logs subscription on the firewall alert log group invokes a Lambda function that writes custom findings to Security Hub CSPM (`BatchImportFindings`, the account's default product ARN). Alerts are grouped per rule, source address and hour.
- **Why:** Network Firewall is not a native finding source. The "AWS service integrations with Security Hub CSPM" page lists Config, Firewall Manager, GuardDuty, Health, IAM Access Analyzer, Inspector, IoT Device Defender, Macie, Route 53 Resolver DNS Firewall and Patch Manager as senders. Firewall Manager covers WAF and Shield policies and needs AWS Organizations; Health sends service events, not traffic alerts. The custom findings are labeled as coming from a custom integration so they are not mistaken for a native one.
- **Rejected:** Claiming a native integration; Firewall Manager (multi-account governance, out of scope).

## ADR-010 - GuardDuty with EKS audit logs, without runtime monitoring

- **Status:** Amended: GuardDuty and Security Hub are Landing Zone services and are no longer enabled here (ADR-017).

- **What:** GuardDuty is enabled with EKS audit log monitoring; runtime monitoring is turned off. Security Hub CSPM is enabled with its default standards.
- **Why:** Runtime monitoring installs an agent DaemonSet on the nodes, and two t3.medium nodes (the account allows 5 vCPU) already run Istio and five services. Both services are on their free trial and are disabled at cleanup.
- **Rejected:** Runtime monitoring (node capacity).

## ADR-011 - Session Manager on an EKS node, no extra instance

- **What:** The zero-open-port admin demo targets an EKS worker node. The node security group has no rule open to the internet and none on port 22. It still has inbound rules from the cluster security group and from itself, which Kubernetes needs (API server to kubelet, pod to pod).
- **Why:** The account's on-demand quota is 5 vCPU and the two nodes use 4, so no separate instance can run. The claim made is therefore "no inbound rule from outside the VPC and no SSH", not "zero inbound rules", because the node security group cannot have zero.
- **Rejected:** A dedicated t3.micro admin target (quota); claiming zero inbound rules on a node.

## ADR-012 - The public entry point stays plain HTTP on port 80

- **What:** The single deliberate ingress is the Istio gateway's load balancer on TCP 80. The firewall inspects the HTTP path and only passes `/api/` requests.
- **Why:** The original platform has no domain and no certificate. Adding TLS would need both and is not part of the retrofit; because the traffic is plaintext, the firewall can read the path, which is what the blocked-path demo uses.
- **Rejected:** Adding a domain and an ACM certificate (outside the scope of the plan).

## ADR-013 - Consume the Landing Zone through remote state, one contract guard per stack

- **What:** Each stack (`infra/cluster`, `infra/data`, `infra/zerotrust`) contains an identical `landing_zone.tf` that reads the Landing Zone outputs with `terraform_remote_state` and enforces a `terraform_data` contract: `contract_schema_version`, primary/DR regions, `require_cmk` (CMKs where required), and the presence of the `shared-applications` ECR repository. State for these stacks lives in the Landing Zone state bucket (`backend "s3" {}` plus `environments/<env>/backend.hcl`, native lock files).
- **Why:** Plans fail early and readably when the Landing Zone changes shape, instead of failing deep inside a resource. The bootstrap stack and its budget/bucket are no longer this repository's job.
- **Rejected:** Looking the VPC up by tag or name (silently picks the wrong thing); a bootstrap stack that creates a state bucket (duplicates the Landing Zone).

## ADR-014 - The VPC, subnets and availability zones come from the Landing Zone

- **What:** The `vpc` module and its NAT/IGW/route tables are deleted. The cluster uses `af_south_1.vpc_id` and `private_subnet_ids`. Subnet tags EKS needs for load balancer discovery are added with `aws_ec2_tag` (additive, no subnet is modified), switchable with `tag_landing_zone_subnets`. Route tables and the IGW, which the Landing Zone does not export, are resolved by data source from the exported subnet and VPC IDs.
- **Why:** Persona rule: never recreate Landing Zone resources.
- **Rejected:** Importing the Landing Zone VPC into this state (two owners for one resource).

## ADR-015 - No NAT: Istio images are mirrored into the Landing Zone shared-platform ECR

- **What:** The Landing Zone exports no NAT address (`nat_public_ips = []`), so no pod can reach Docker Hub. `scripts/mirror_istio_images.sh` copies `pilot` and `proxyv2` into the shared-platform repository as tags (`pilot-1.30.2`, `proxyv2-1.30.2`), and `operator.yaml` references them by full image path. The five services use one shared-applications repository with `<service>-<version>` tags. `egress_allowed_domains` defaults to empty.
- **Why:** Creating a NAT gateway would add a billed, internet-facing resource the Landing Zone chose not to have. Per-service ECR repositories would recreate what the Landing Zone already provides.
- **Check after install:** confirm the Istio image paths with `kubectl get pods -A -o jsonpath` after the first install.
- **Rejected:** NAT behind the firewall (ADR-008 original); one ECR repository per Istio image (not provided by the Landing Zone).

## ADR-016 - Routing changes to Landing Zone route tables are explicit and off by default

- **What:** The firewall subnet, its route table, the firewall, policy and logs are new resources. Adding `0.0.0.0/1` and `128.0.0.0/1` routes to the Landing Zone public route tables and associating an edge route table with the IGW are done only when `inspect_public_subnets = true`. A plan-time check rejects a firewall subnet CIDR that is outside the VPC or overlaps an existing subnet.
- **Why:** Those routes change how a Landing Zone-owned network behaves, so the Landing Zone owner approves them; dev and test default to off, the prod example file turns it on.
- **Rejected:** Replacing the Landing Zone default route (it is not ours to edit).

## ADR-017 - GuardDuty, Security Hub, flow logs and the account Session Manager document are conditional

- **What:** No detector or Security Hub account is created. The EKS audit-log feature on the existing detector is opt-in (`manage_guardduty_eks_audit_logs`). Firewall-to-Security Hub findings run only when the Landing Zone reports `security_hub_enabled = true` (it is `false` today). Workload flow logs are off by default and refused when the Landing Zone already exports flow logs (it exports none today). The `SSM-SessionManagerRunShell` document is an account singleton: `manage_session_preferences` turns it off if the Landing Zone owns it.
- **Why:** These are shared, account-level controls. Creating them here would recreate or fight Landing Zone resources.

## ADR-018 - Encryption follows the Landing Zone key strategy

- **What:** `key_strategy = aws-managed` (dev): DynamoDB, SQS, S3 session logs and EKS secrets use AWS-managed or service-owned encryption. prod sets `require_cmk = true`, which makes the plan fail unless the Landing Zone exports CMKs (`shared_kms_keys`); the repository never creates a key. dev and test use AWS-managed keys.
- **Why:** The persona's FinOps encryption rule: AWS-managed keys in dev/test, CMKs in production.

## ADR-019 - Service Regional Availability: deploy from eu-west-1 when af-south-1 lacks a service

- **What:** On 2026-11-26 every service this repository uses was found available in af-south-1 (docs/regional-availability.md), so nothing is deployed from Ireland and no `ireland` alias is declared. If a service fails the check, the alias is added for that resource only.
- **Why:** The persona now says a service that is not available or not generally available in South Africa is deployed from Ireland, the DR region.
- **Rejected:** Deploying anything to us-east-1 (as the original build did) or any region other than the two approved ones.

## ADR-020 - One repository, three stacks, `provider.tf` in each

- **What:** The two zero trust repositories are merged into `aws-zero-trust-network`. Stacks live at `infra/cluster`, `infra/data` and `infra/zerotrust`; each has `provider.tf` (Terraform block, partial S3 backend, provider) and the identical `landing_zone.tf`. Separate states keep the cluster, data and controls lifecycles independent.
- **Why:** One root module would couple an EKS replacement to firewall and IAM changes. The second repository's modules mostly duplicated Landing Zone services.
- **Rejected:** One root module with all resources; keeping two repositories.

## ADR-021 - Engineer role is optional and MFA-gated

- **What:** `engineer_access.tf` creates a break-glass role, permission boundary and scoped policy only when `engineer_trusted_principal_arns` is not empty. Trust requires MFA no older than one hour; sessions last at most `engineer_session_seconds` (default 3600). A Region deny limits calls to af-south-1 and eu-west-1.
- **Why:** The Landing Zone provides Identity Center permission sets for routine access; this role covers emergencies and keeps the NIST identity tenets visible. An empty trust list never falls back to `*`.
- **Rejected:** Creating an Access Analyzer (the Landing Zone owns one); IAM users.

## ADR-022 - Tier security groups are optional

- **What:** `tier_segmentation.tf` creates web, app and db security groups in the Landing Zone VPC when `create_tier_security_groups = true`, with security-group-to-security-group rules only.
- **Why:** Useful for non-EKS workloads; EKS pods are already isolated by the firewall, Istio and security groups of the cluster. Off by default to avoid idle resources.
- **Rejected:** Creating a second VPC for segmentation.

## ADR-023 - EKS Terraform module 21.x and AWS provider 6.x

- **What:** `terraform-aws-modules/eks/aws ~> 21.0` with the renamed inputs (`name`, `kubernetes_version`, `endpoint_*_access`, `encryption_config`); all stacks pin the AWS provider `>= 6.27.0, < 7.0`.
- **Why:** Module 21.x requires provider 6.x, which is the repository-wide pin.
